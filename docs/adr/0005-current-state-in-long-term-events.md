# いまの状態は長いイベントだけが持ち、作り直して照合する

## 状況と問題

状態(status)を、いろいろなモデルが自分で書き換えていた。どれが正しい状態かを、ほかの記録から確かめる方法がなかった。

## 判断の基準

* 状態を書き換える場所が少ないこと
* 状態が、元の出来事と食い違っていないことを確かめられること

## 検討した選択肢

* 状態の列を持たず、毎回イベントから計算する
* 長いイベントだけが「いまの状態」の列を持ち、詳細のイベントの入口だけが書き換える。イベントから作り直して照合する

## 決定

採用:「長いイベントだけがいまの状態を持ち、照合する」。理由: 一覧の画面で毎回計算すると重い。列を持つなら、作り直して照合できることを条件にする。

* 例: 証憑(Voucher)の status は、提案のイベント(承認・却下・取り下げ)から決まる(derived_status)。書き換えるのは入口の中の advance_status! だけ。
* 提案のイベントから決まらない状態(AI の作業中・エラー・記帳しない)は、そのまま持つ。
* リソースには状態を持たせない。

### 結果

* 良い: 状態がずれたら bin/rails model:verify で分かる。
* 悪い: 照合の決まりを、長いイベントごとに書く必要がある。

### 確かめ方

bin/rails model:verify(app/models/model_verification.rb)。CI でも流す。手元のデータでも流す。
