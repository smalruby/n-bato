# PDF は AWS Lambda の Chromium で作り、Rails はジョブから S3 を通して頼む — 開発QAボード 第7回

## 状況と問題

書類(事業報告書等・計算書類・決議・登記の添付書類・元帳・様式の例)の PDF は、6 つのコントローラーがリクエストの中で Rails のサーバーのヘッドレス Chrome を立ち上げて作っている。Chrome はメモリを食い、負荷で立ち上がりが遅れて失敗し(#9)、Chromium の更新を追い続けることになる。PDF をどこで、どう待って、どう渡して作るか(Issue #22)。

## 判断の基準

* いまの印刷用の HTML をそのまま使い、書類の見た目を変えない
* 本番のサーバー(Lightsail 2GB)のメモリと手間を減らす
* **強さ**: 過去に Lambda 上の Chromium で「メモリが 100MB を超えると止まる」「通信の失敗のやり直しが適切でない」ことがあった。PDF を作ることは大事(第7回 r7-when のひとこと)
* 書類の中身(役員の氏名・住所、金額)を外に出さず、残しすぎない
* 書類を出す時期にも壊さない(12 月に止める期間は設けない。2026-11-24 理事長「改修はどんどんやって、問題があれば都度直す」。受け入れの条件と手で戻すスイッチで守る)

## 検討した選択肢

* AWS Lambda(Chromium と日本語のフォントを入れたコンテナ)で作り、Rails はジョブから頼む
* ブラウザの印刷で PDF にする(サーバーでは作らない)
* Ruby だけで PDF を組み立てる(Prawn など)
* (待ち方)リクエストの中で Lambda を呼んで待つ

## 決定

採用:「Lambda で作り、Rails はジョブから頼む」(第7回 r7-where・r7-wait・r7-data・r7-key・r7-when、5 問ともおすすめ)。理由: いまの HTML が使え、Lambda は使ったときだけ動き、Rails のイメージから Chromium を外せる。中身の設計は [docs/design/pdf-lambda.md](../design/pdf-lambda.md)。

* **流れ**: コントローラーが書類の目録(`PrintDocument`)から印刷用の HTML を作り、内容のハッシュ(`input_key`)と作り手(`renderer_key` = エンジン・ビルド・フォントの digest)が同じできた PDF があればそれを出す。無ければ `PdfRendering`(長いイベント)を作り、HTML は SQLite に入れず一時ファイルに置く。ジョブ(キュー `pdf`)が HTML を S3 に置いて Lambda を **同期(RequestResponse)** で呼ぶ。Lambda は PDF をストリームで受けて S3 に置く。ジョブがそれを Active Storage に添付し、ログインした人だけに渡す。画面は「作っています」→「開く」(画面は見直し票で決める)。
* **プロトコル**: Lambda に渡すのは参照だけの JSON。JSON Schema は `lambda/pdf-renderer/schema/*.v1.json` の 1 か所で、Rails と Lambda の両方のテストが使う。S3 のキーは `v1/in/<id>-<input_key>.html` と `v1/out/<input_key>/<renderer_id>.pdf`。署名付き URL は使わない。
* **S3**: PDF 専用のバケット。非公開・SSE-S3・TLS だけ・1 日で消える(途中のマルチパートも)。ふだんは添付したすぐあとに消す。ログには中身を書かず、Lambda の失敗の本文も Rails のログに出さない。
* **やり直すのはジョブだけ**: Lambda は自分でやり直さない。Ruby の SDK の Lambda の呼び出しは `retry_mode: "standard", max_attempts: 1` を明示する(既定は 3 回で、`Net::ReadTimeout` もやり直す)。読み取りの待ち時間 100 秒は関数の時間切れ 90 秒より長くする。ジョブは失敗を 8 つに分類し(一時的・結果が分からない・重い入力・入力が悪い・途中で壊れた・期限切れ・設定の誤り・予想していない)、DB の試みの回数で数えて、分類ごとに回数と待ちを決める。
* **二重に作らない(3 つ)**: できた PDF の使い回し・作っている途中への合流(部分の一意の索引)・出力の条件つきの書き込み(`If-None-Match: *`。412 はある方を使う)。Rails は S3 のオブジェクトのチェックサムで中身を確かめる。状態は条件つきの UPDATE で移し、ジョブが二度動いても壊さない。
* **メモリ**: 関数は 1 つ。**なるべく少なく**(開発QAボード 第9回): 1024MB から始め、P1 の実験で 512〜1536MB を比べ、6 つの書類とストレスが作れ、メモリの山が 50% 以下・時間が時間切れの半分以下のいちばん小さい値にする。1024MB で足りなければ、測った表を付けてこの ADR を書き足す。メモリの山は REPORT の `Max Memory Used` を正とし、毎回記録して 50% で警報。過去の「100MB で止まる」は、関数のメモリ(当時 6GB)ではなく Chromium の側の上限(起動の旗か環境変数)だった(開発QAボード 第8回、[Issue #22](https://github.com/smalruby/n-bato/issues/22#issuecomment-7138129159))。どの上限か(共有メモリ・V8 のヒープ・`--single-process` など)は P1 の実験で、いまの Chrome と Lambda の包みの既定の旗で再現してから確かめ、メモリに効く旗を一覧に書いてテストで固定する。
* **通信の禁止**: VPC には置かず、Lambda の Chromium は `data:` 以外の要求をすべて止め、JS を止める。Runtime API(`127.0.0.1:9001`)なども攻撃のテストで確かめる。費用は AWS Budgets で見張る。
* **豆腐**: Lambda はフォントに無い字の数(`missing_glyphs`)を返す。運用の側が、本番の文の字がフォントにあるかを件数と U+ だけで点検する。
* **鍵**: PDF 専用の IAM ユーザー(ADR-0035)。この関数を呼ぶことと、PDF のバケットの決まった場所の読み書き・消すことだけ(ListBucket なし)。
* **切り替え**: 先にジョブの流れを Chrome のまま出し、そのあとエンジンを `NBATO_PDF_ENGINE=lambda` に切り替える。条件は、運用の側が本番で **すべての年度・決議・登記の 6 つの書類** を Lambda で作って捨て、失敗 0・ページ数が Chrome と同じ・足りない字 0・いちばん重いもののメモリが 50% 以下。条件が通ったらすぐ切り替える(12 月に止める期間は設けない)。Chrome へは **手で** 戻す(自動では戻さない)。最後の逃げ道はブラウザの印刷。

### 結果

* 良い: 本番のサーバーで Chrome が動かなくなり、メモリの山と立ち上がりの失敗(#9)がなくなる。PDF が添付として残り、同じ書類は作り直さない。ジョブの進み具合(#23)の土台になる。
* 悪い: 部品が増える(Lambda・ECR・S3・VPC・IAM ユーザー・Node.js のコード)。Chromium の版を Lambda のイメージで追うことになる。PDF がすぐには開かず、待つ画面が入る(使い回しのときはすぐ開く)。

### 確かめ方

* Lambda の中の単体テスト(要求の形・期限・条件つきの書き込み・上限・時間切れ・旗の一覧・ログに中身が出ないこと)。手元のコンテナは Lambda に近づけて動かす(読み取り専用・/tmp の大きさ・root でない)。
* 架空のデータの 6 つの書類とストレス(300 ページ・画像・長い表)を、いまの Chrome と Lambda で作り、ページ数・文字・フォント・画像の差(0.5% 以下、仮)で見比べる。通信の禁止の攻撃のテスト。同時 10 と、続けて 50 回の負荷のテスト。
* Rails のテストは Fake で、SDK の設定(`max_attempts == 1`・読み取りの待ち > 関数の時間切れ)・失敗の分類ごとのやり直しの回数・状態の移り変わりの排他・二重に作らないこと・見てよい人にだけ PDF を出すことを確かめる。
* 本番での受け入れ(すべての書類を作って捨て、数だけを見る)を、切り替えの条件にする。
* CDK のテストで、バケットの設定・IAM の権限の対象・関数の設定を確かめる。
* 設計を別の Agent に敵対的にレビューさせてから作る(第7回 r7-when)。1 回目のレビューの対応は設計書の「レビューへの対応」。

## 選択肢ごとの良い点と悪い点

### Lambda で作り、ジョブから頼む

* 良い: いまの HTML がそのまま使える。使ったときだけ動き、無料枠の中の見込み(月 1 ドルより少ない)。
* 悪い: 部品が増える。Lambda 上の Chromium は過去に不安定だった(→ メモリの測り方・やり直しの決まり・本番での受け入れで抑える)。

### ブラウザの印刷

* 良い: 運用の手間が 0。
* 悪い: 1 つずつ人が保存する。余白やヘッダーがブラウザの設定で変わる。まとめて作る・メールに添えることができない。→ 失敗したときの最後の逃げ道としてだけ残す。

### Ruby だけで組み立てる

* 良い: Chrome が要らない。
* 悪い: 書類ごとに配置を作り直し、いまの HTML が使えない。

### リクエストの中で Lambda を待つ

* 良い: 画面が変わらない。
* 悪い: 立ち上がりが遅いとき proxy の待ち時間(30 秒)に当たる。

## 補足

* Issue #22(決まったこと: 開発QAボード 第7回。第9回(2026-11-25)でこの設計を通し(`r9-adr0037`、おすすめ。ひとこと「なるべくメモリを少なく、1GB か、できれば 500MB 程度。実験して適切な値に」)、作った PDF は書類ごとに一番新しいものを残して古いものは 30 日で消すに決めた(`r9-pdf-keep`、おすすめ))、ジョブの進み具合の画面は EPIC #23、Chrome を立ち上げないテスト(Fake)は #9・PR #21。
* 関係する ADR: ADR-0005(長いイベント)、ADR-0008(出来事は create)、ADR-0012(画面の変更は見直し票から)、ADR-0035(用途ごとの IAM ユーザー)。
* **P1 の実験の結果(2026-11-27、PR #64)**: 測った表は [設計の 4.10.1](../design/pdf-lambda.md)。
  * **関数のメモリは 768MB**(1024MB より小さくした。理事長「Lambda のメモリが少なくてよいのはメリットが大きい」。512MB は画像の大きな書類で山が 65% になり、50% の条件を外れる)。
  * **1 回に作るのは 25 ページまで**(理事長「300 ページの帳簿は対象外でいい。最大 25 ページ、それ以上はジョブを分割に。いまのところそのような帳票はない」)。300 ページの元帳は山が約 1,425MB で、50% 以下には 3,008MB が要った。
  * **Chromium は Chrome for Testing の `chrome-headless-shell`**(158.0.8127.88、zip を SHA-256 で固定)。`@sparticuz/chromium` は 143〜158 のどの版も、x86_64 の ubuntu と Lambda のイメージで立ち上がらなかった。
  * 「100MB で止まる」は、いまの Chromium と旗では再現しなかった(共有メモリ・V8 のヒープ・`--single-process` のどれを変えても同じ)。旗は変えない。
* 見直す時期: P1(手元のコンテナで測ったあと)にメモリ・閾値を、切り替えの数週間後に Rails のイメージから Chromium を外すかを決める。
