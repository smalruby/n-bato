# PDF は AWS Lambda の Chromium で作り、Rails はジョブから S3 を通して頼む — 開発QAボード 第7回

## 状況と問題

書類(事業報告書等・計算書類・決議・登記の添付書類・元帳・様式の例)の PDF は、6 つのコントローラーがリクエストの中で Rails のサーバーのヘッドレス Chrome を立ち上げて作っている。Chrome はメモリを食い、負荷で立ち上がりが遅れて失敗し(#9)、Chromium の更新を追い続けることになる。PDF をどこで、どう待って、どう渡して作るか(Issue #22)。

## 判断の基準

* いまの印刷用の HTML をそのまま使い、書類の見た目を変えない
* 本番のサーバー(Lightsail 2GB)のメモリと手間を減らす
* **強さ**: 過去に Lambda 上の Chromium で「メモリが 100MB を超えると止まる」「通信の失敗のやり直しが適切でない」ことがあった。PDF を作ることは大事(第7回 r7-when のひとこと)
* 書類の中身(役員の氏名・住所、金額)を外に出さず、残しすぎない
* 12/7〜12 月中の書面決議・登記の時期に壊さない

## 検討した選択肢

* AWS Lambda(Chromium と日本語のフォントを入れたコンテナ)で作り、Rails はジョブから頼む
* ブラウザの印刷で PDF にする(サーバーでは作らない)
* Ruby だけで PDF を組み立てる(Prawn など)
* (待ち方)リクエストの中で Lambda を呼んで待つ

## 決定

採用:「Lambda で作り、Rails はジョブから頼む」(第7回 r7-where・r7-wait・r7-data・r7-key・r7-when、5 問ともおすすめ)。理由: いまの HTML が使え、Lambda は使ったときだけ動き、Rails のイメージから Chromium を外せる。中身の設計は [docs/design/pdf-lambda.md](../design/pdf-lambda.md)。

* **流れ**: コントローラーが印刷用の HTML を作り、内容のハッシュ(cache_key)で、できた PDF があればそれを出す。無ければ `PdfRendering`(長いイベント)を作り、ジョブ(キュー `pdf`)が HTML を S3 に置いて Lambda を **同期(RequestResponse)** で呼ぶ。Lambda は S3 から読み、PDF を S3 に置く。ジョブがそれを Active Storage に添付する。画面は「作っています」→「開く」(画面は見直し票で決める)。
* **プロトコル**: Lambda に渡すのは参照だけの JSON(版・cache_key・S3 のキー・ハッシュ・上限・期限)。S3 のキーは `v1/in/<cache_key>.html`・`v1/out/<cache_key>.pdf`。署名付き URL は使わず、IAM の権限で読み書きする。
* **S3**: PDF 専用のバケット。非公開・SSE-S3・TLS だけ・1 日で消える(ふだんは添付したすぐあとに消す)。ログには中身を書かない。
* **やり直すのはジョブだけ**: Lambda は自分でやり直さず(同期の呼び出し、非同期のやり直し 0)、Ruby の SDK も Lambda の呼び出しをやり直さない(`max_attempts: 1`、読み取りの待ち時間 100 秒 > 関数の時間切れ 90 秒)。ジョブは失敗を分類し(一時的・結果が分からない・重い入力・入力が悪い・設定の誤り)、分類ごとに回数・待ち(指数 + ゆらぎ)を決める。
* **二重に作らない**: できた PDF の使い回し・作っている途中への合流(部分の一意の索引)・同じ cache_key のジョブは同時に 1 つ・Lambda は出力があれば作らない・SDK はやり直さない。
* **メモリ**: 2048MB から。毎回メモリの山を測って記録し、警報を付ける。重い入力の 2 回目は 4096MB の関数に回す。ストレスのテストを半分のメモリで通すことを切り替えの条件にする。
* **通信の禁止**: Lambda の Chromium は `data:` 以外の要求をすべて止め、JS を止め、外へ出られない網(VPC、NAT なし、S3 だけエンドポイント)に置く。
* **鍵**: PDF 専用の IAM ユーザー(ADR-0035)。できるのは、この関数を呼ぶことと、PDF のバケットの決まった場所の読み書き・消すことだけ。
* **切り替え**: 先にジョブの流れを Chrome のまま出し、そのあとエンジンを `NBATO_PDF_ENGINE=lambda` に切り替える。12/3 までに確かめが通らなければ 1 月。しばらく Chrome に戻すスイッチ(手で戻す・一時的な失敗のときは 1 件ずつ Chrome で作る)を残す。

### 結果

* 良い: 本番のサーバーで Chrome が動かなくなり、メモリの山と立ち上がりの失敗(#9)がなくなる。PDF が添付として残り、同じ書類は作り直さない。ジョブの進み具合(#23)の土台になる。
* 悪い: 部品が増える(Lambda・ECR・S3・VPC・IAM ユーザー・Node.js のコード)。Chromium の版を Lambda のイメージで追うことになる。PDF がすぐには開かず、待つ画面が入る(使い回しのときはすぐ開く)。

### 確かめ方

* Lambda の中の単体テスト(要求の形・期限・出力の使い回し・上限・時間切れ・ログに中身が出ないこと)。
* 架空のデータの 6 つの書類とストレス(300 ページ・画像・長い表)を、いまの Chrome と Lambda で作り、ページ数・文字・フォント・画像の差(0.5% 以下、仮)で見比べる。通信の禁止の攻撃のテスト。同時 10 と、続けて 50 回の負荷のテスト。
* Rails のテストは Fake で、失敗の分類ごとのやり直しの回数・二重に作らないこと・ログインなしで PDF を出さないことを確かめる。
* CDK のテストで、バケットの設定・IAM の権限の対象・関数の設定を確かめる。
* 設計を別の Agent に敵対的にレビューさせてから作る(第7回 r7-when)。

## 選択肢ごとの良い点と悪い点

### Lambda で作り、ジョブから頼む

* 良い: いまの HTML がそのまま使える。使ったときだけ動き、無料枠の中の見込み(月 1 ドルより少ない)。
* 悪い: 部品が増える。Lambda 上の Chromium は過去に不安定だった(→ メモリの測り方・やり直しの決まりで抑える)。

### ブラウザの印刷

* 良い: 運用の手間が 0。
* 悪い: 1 つずつ人が保存する。余白やヘッダーがブラウザの設定で変わる。まとめて作る・メールに添えることができない。→ 失敗したときの最後の逃げ道としてだけ残す。

### Ruby だけで組み立てる

* 良い: Chrome が要らない。
* 悪い: 書類ごとに配置を作り直し、いまの HTML が使えない。

### リクエストの中で Lambda を待つ

* 良い: 画面が変わらない。
* 悪い: 立ち上がりが遅いとき proxy の待ち時間(30 秒)に当たる。
