# 開発と運用の大きな方針

## 状況と問題

NPO 法人の事務(会計・会員・所轄庁への提出など)を引き受けるアプリを、AI が設計・実装し、人(理事長)が確かめて承認する形で作る。帳簿の正をどこに置くか、どこで動かすか、AI に何を任せるかを決める。

## 検討した選択肢

* 帳簿の正: はじめからこのアプリ / 当面は会計ソフト(会計王)を正にし、このアプリはその仕訳形式で読み書きする
* 動かす場所: はじめから本番(クラウド) / まず手元の Docker
* AI の仕訳: AI が記帳する / AI は提案し、人が承認してから記帳する
* 進め方: 人が 1 つずつ指示する / 合意したことは AI が自律で反映し、判断が要るものは推奨を採用して記録、決められないものは保留して、まとめて人に確かめる

## 決定

* 帳簿の正は当面、会計ソフト。仕訳は会計ソフトの形式(SIWAKE 3.00.00)で読み書きし、書き出したものを元と同じバイト列にする。数年後にこのアプリを正にすることを目指す
* まず手元の Docker で動かす。本番は Lightsail と Kamal(ドメインとステージングは後で)
* AI は仕訳を提案し、人が承認してから記帳する。仕訳には元の証憑・AI の根拠・承認者と日時を残す
* 合意済みのことは AI が自律で反映する。判断が要るものは選択肢を記録して推奨を採用し、決められないものは保留にして、まとめて人に確かめる。最後に人が画面で確かめられる状態にする
* 外の仕組み(Slack など)とつなぐときは、組み込む前に人と一緒に実際に動くかを確かめる
* 公開・共有の設定(誰が見られるか)は人が行い、AI は設定を読んで確かめるだけにする

### 理由

* 会計ソフトは電子帳簿の要件などを満たしているので、すぐに置き換えない(人の判断)
* 推測: 使う人が少ないうちは、手元で速く回して形を固めるほうがよい
* 推測: お金と個人情報に関わる操作は、最後に人が決める形にしておく

## 補足

* 予算の機能は、人もまだ形を決めていないので、作業しながら一緒に作る(ADR-0015)。
* 公開までの順番: パスキー → イミュータブルデータモデルへのリファクタリング → バックエンドのテストのカバレッジ 100% → 公開 → ドメイン → 本番での試運転。
