# イミュータブルデータモデルを土台にする

## 状況と問題

1 つの行を何度も書き換える作りが多かった。例えば AI の提案(JournalProposal)は、1 行に提案した日時・確認した日時・状態・できた仕訳を持ち、承認のたびに書き換えていた。書き換えには「この画面のときはこの列だけ」のような決まりが付きまとい、その決まりはモデルからは読めない。

## 判断の基準

* 業務の出来事(いつ・誰が・何をしたか)が、そのまま記録に残ること
* 書き換えの決まりを減らし、AI が作っても複雑さが増えないこと
* 会計の決まり(記帳したら書き換えず、訂正の仕訳で直す)と合うこと

## 検討した選択肢

* いままでどおり、行を書き換えて状態を持つ
* イミュータブルデータモデル(リソースとイベントを分け、イベントは追加だけ)
* イベントソーシング(すべてをイベントから組み立てる。rails_event_store など)

## 決定

採用:「イミュータブルデータモデル」。理由: 出来事が日時付きで残り、書き換えの決まりが要らなくなる。イベントソーシングほど仕組みを足さずに、Active Record のまま書ける。

* 5W1H のうち、誰・何・いつ・どこはリソース(R)、なぜ・どうやってはイベント(E)。エンティティ名に「〜する」を付けて自然ならイベント。
* イベントは日時を 1 つだけ持ち、追加するだけ(ADR-0003)。
* 始まりと終わりのある出来事(入会・証憑の処理・依頼・手続き・決議)は長いイベント(LE)。中の詳細のイベントを足していき、長いイベントは「いまの状態」だけを持つ(ADR-0005)。
* どちらがなくても成り立つもの同士(人と年度、人と役)は、外部キーを持たせずに交差エンティティで結ぶ。
* 分け方は台帳(docs/data-model.md)に書く。マスタ・トランザクションという分け方は使わない。

### 結果

* 良い: 「いつ誰が承認したか」が承認のイベントとして残る。書き換えの決まりが減る。
* 悪い: テーブルの数が増える(AI が作るので手間は小さい)。いまの状態を出すのに、詳細のイベントを引く必要がある。

### 確かめ方

台帳に全モデルの分類が書いてあることをテストで確かめる(test/models/data_model_ledger_test.rb)。

## 補足

* 出どころ: kawasima「イミュータブルデータモデル」。37signals の Recordables(中身は書き換えずに新しく作り、変更の記録は Event に残す)と、Rails の delegated_type も参考にした。
* 移す順は、会計 → 会員 → やること・依頼 → 手続き・決議・提出・登記。最初の会計は 2026-11-23 に移した(AI の提案・承認・却下・取り下げ)。
