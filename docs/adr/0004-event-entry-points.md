# イベントを作る入口

## 状況と問題

書き込みの処理が、コントローラーとモデルのメソッドに散らばっていた。理事長の案は Account::Event.call(...) の形。Rails の名前の付け方に合わせて、入口の形を決める。

## 判断の基準

* どこで出来事が起きるかが、名前から分かること
* 1 つの出来事の処理(確かめ・追加・関係するイベント・いまの状態・操作履歴)が 1 か所にまとまること
* サービス層のような層を足さないこと(Rails の流儀)

## 検討した選択肢

* リソースの名前空間に、出来事の名詞のクラスを置き、入口はクラスメソッド 1 つ
* 1 つの入口(Account::Event.call(type: ...))から種類で振り分ける
* サービスオブジェクト(app/services)

## 決定

採用:「リソースの名前空間に出来事の名詞のクラス、入口はクラスメソッド 1 つ」。

* 名前は出来事の名詞: 承認 = JournalProposal::Approval、却下 = JournalProposal::Rejection。
* 入口のメソッド名は、出来事に合う英語の動詞にする(approve!・reject!・withdraw!・propose!)。call が合わないことも多いので固定しない(理事長の判断)。迷ったら record!。
* 入口は 1 つのトランザクションで、確かめ・イベントの追加・関係するイベント(承認 → 仕訳)・長いイベントのいまの状態・操作履歴の名前まで行う。
* 入口は event_of の entry: で宣言する(テストが読む)。

### 結果

* 良い: 「承認」を探せば JournalProposal::Approval.approve! にたどり着く。
* 悪い: クラスの数が増える。

### 確かめ方

ADR-0003 のテストで、宣言した入口があること、ほかから create していないことを確かめる。
