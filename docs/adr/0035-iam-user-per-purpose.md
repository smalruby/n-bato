# 本番が AWS を使う鍵は、用途ごとに IAM ユーザーを分け、できることを絞る — 開発QAボード 第7回

## 状況と問題

本番のサーバー(Lightsail)には AWS の役割(ロール)を付けられないので、本番から AWS を使うには IAM ユーザーの鍵が要る。いまはバックアップ用(S3)と SES 用がある。PDF を Lambda で作る(#22)と、Lambda を呼ぶ鍵も要る。新しい用途ができるたびに、鍵をどう分けるかを聞くか、決まりにしておくか。

## 判断の基準

* 鍵が漏れたときの害を小さくする(できることを用途の分だけにする)
* 毎回聞かずに進められる(決まりにして、確かめる回数を減らす)

## 検討した選択肢

* 用途ごとに IAM ユーザーを作る
* いまある IAM ユーザー(バックアップ用など)にできることを足していく

## 決定

採用:「用途ごとに IAM ユーザーを作る」。理由: 漏れたときに止めるのがその用途だけで済み、権限の範囲も読みやすい(第7回 r7-key。理事長「この方針を ADR に記載して、いちいち確認しない。用途ごとに IAM を作る」)。

* 1 つの用途に 1 つの IAM ユーザー。権限は、その用途のリソース(関数・バケットの中の決まった場所など)に限る。ワイルドカードで広げない。
* IAM ユーザーと権限は `infra/` の CDK に書く。鍵(アクセスキー)はスタックに入れず、`bin/infra-credentials` で作って秘密の置き場所に入れる(第3回の決まりのまま)。
* **この形の IAM ユーザーを足すことは、いちいち人に聞かない。** CDK の反映(cdk deploy)・鍵の受け渡し・本番の秘密に入れることは、これまでどおりその都度確かめる。

### 結果

* 良い: 用途を足すたびの相談が要らない。漏れたときの害が用途の中に収まる。
* 悪い: 鍵の数が増え、回すとき(作り直すとき)の手間が増える。
