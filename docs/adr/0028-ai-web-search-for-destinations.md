# 提出先の窓口を AI に Web で調べてもらう

出どころ: 見直し票 第17回。ADR-0027 を受ける。

## 状況と問題

所在地から所轄庁・県税事務所・市町村の税の窓口・法務局・税務署を人が調べるのは手間がかかる。一方で、AI の調べものを確かめずに書類に使うと、間違った宛先で出してしまう。

## 判断の基準

* 外に送るのは必要な最小限(法人の所在地と法人の種類だけ。会員の情報は送らない)
* AI の案と、人が確かめた情報を見分けられること
* 外部連携は、組み込む前に人と一緒に実際に動くかを確かめること

## 検討した選択肢

* Claude API の Web 検索(サーバーツール `web_search_20260209`)で調べ、案を出す(採用)
* AI には調べさせず、人が入力する

## 決定

採用:「AI に調べてもらう」。`FilingDestinationSearch`(長いイベント。いまの状態は status)が `Bookkeeper::Client#search_json` で Web 検索つきの答え(JSON Schema)を受け取り、出どころの URL がある窓口だけを「AI の案」(origin = ai)として提出先に足す。人が出どころのページを見て「確認済み」にするまで、書類には使わない(ADR-0027)。調べている間は「待つ表示」(15 秒ごとに読み込み直す)。

* 鍵(ANTHROPIC_API_KEY)が無ければ、ボタンを出さずに手で入れてもらう。
* 自動テストは偽のクライアントで行い、実際の呼び出しは人と一緒に確かめてから使い始める(`search_json` も、偽の API(FakeClaudeApi)で Web 検索の続き・エラーまで自動テストで確かめる。issue #6)。

## 結果

* 良い: 最初の起動で、窓口の案と出どころがそろう。
* 悪い: Web 検索の費用がかかる。案が古いページから来ることがあるので、人の確認は省けない。

## 確かめ方

`test/models/filing_destination_test.rb`(偽のクライアントで、送る文に所在地だけ・出どころの無い案は足さない・失敗の記録)。実際の呼び出しは、人と一緒に 1 回確かめる。
